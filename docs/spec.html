全体の作り

フロント（地図）とバックエンド（サーバー）は、別々のリポジトリ・別々の置き場所で

動いています。地図の中の API_BASE がサーバーの絶対URLを指し、

CORSでGitHub Pagesからの呼び出しだけを許可しています。

Renderの無料プランは、しばらく誰も使わないと休止します。

次のアクセスで起き上がるまで50秒ほどかかります（コールドスタート）。

曲名検索（これなんて曲？）

音を聴かせて、曲名とジャンルを当てる機能です。次の順に試します。

1. Shazam（RapidAPI経由）で曲名・アーティスト名を特定する

2. Wikidata でアーティスト→曲の順に genre（P136）を探す。

見つかればそのまま採用し、Geminiは使わない

3. Wikidataに無ければ Gemini に音声と曲名を渡して判断させる。

temperature=0、複数モデルの自動切り替えあり

音声が10,000バイト未満なら「音が検出できませんでした」と返し、Geminiには送りません。

結果はジャンルのタグで出ます。タップで選び、「ジャンルマップで確認する」を押すと

選んだジャンルだけを地図上で光らせます。履歴はブラウザ側（localStorage、最大15件）に

残ります。

cross_checkは「直した文章」ではなく指摘レポートを返します。

指摘が出た場合は、そのレポートをClaudeに渡して本文を直させます。

チョロさんが手で直す必要はありません。

代表曲の動画（v2.07〜）

以前は検索結果の上位2本をそのまま入れていたため、まったく別の動画が

登録されていました（Chiptuneの代表曲にArduinoの電子工作の解説動画など）。

今は次の順に確かめます。

1. 重複していないか … 他のジャンルの代表曲と同じ曲は使わない

2. 段階的な検索語 … 「演奏者＋曲名」から順に、当たるまで語を変える

3. 動画の照合 … 曲名が題名か投稿者名にあるか／演奏者が投稿者名にいるか、

または題名が演奏者名から始まるか／日本で見られるか／カバーや解説動画でないか

4. 通らなければ採らない … 無理に入れず、その代表曲ごと落とす

5. 0曲になったら警告 … 承認画面に出して、生成し直せるようにする

「題名の先頭のかたまり」で演奏者を判定しているのは、名前がどこかにあるだけだと

別物が通るためです（会場名が一致した例、プロレスの試合が通った例があります）。

守っていること（過去に事故が起きたので入れた安全策）

  • 既存のジャンルIDは省略せず全件渡す。 以前は先頭50件だけ渡していて、

存在しないIDを推測して書く原因になっていた

  • 生成に失敗したときは、必ず理由を添える。 「失敗しました」だけでは、

利用上限なのか通信エラーなのか、申請した人にも管理者にも分からない

  • リンク先IDの自動補正（_auto_correct_link_targets）。

既存ラベルとの正規化一致で、誤ったIDを直す

  • 直した結果が不完全なら捨てる。 必須の項目が欠けていたら、直したものを

採用せず元のままにする。ファクトチェックが本文を丸ごと落とす事故を防ぐため

  • 書き込み前にJavaScriptの構文検査（_html_is_valid_js →

check_html_syntax.js）。壊れる場合は書き込み自体を中止する

修正依頼

指摘を受け取ったら、まずClaudeが「文章の指摘」か「動画の指摘」かに分けます

（_triage_correction）。

  • 文章の指摘 … Claudeが既存の説明文とリンク先の内容と照らして事実確認する

（_judge_text_correction）

  • 動画の指摘 … Geminiが動画を実際に視聴し、ジャンルと合っているか判定する

（_judge_video_correction）。合っていなければ、代表曲側の確認済み動画から

差し替え候補を自動で作る

Geminiは無料枠の上限に当たると自動で別のモデルに切り替わります

（_gemini_generate）。承認・却下・「間違いではない」のどの結果でも、

依頼してくれた方への感謝の言葉を末尾に添えます（THANK_YOU_MESSAGE）。

動画の健全性チェック（管理者用）

一般の方向けではない内部機能です。

1. 全件スキャン … YouTubeのタイトルを取得し、ジャンル名との一致度から

機械的に「要確認」を抜き出す（無料・無制限だが誤検知は多い）

2. Geminiで絞り込み … 「要確認」だけをGeminiが実際に視聴する。

1回で最大60件。続きは gemini_verify_state.json に進捗を保存して次回に持ち越す

3. 結果の分類 … 「確実に間違い」「動画が長すぎて確認不可」

「エラーで確認不可」「未着手」の4つに分けて出す

  • 地図の本体（genre_roots.html）… 処理前に _sync_roots_repo で最新化し、

承認時にコミット・プッシュする（push_to_github）

  • 承認待ちのデータ（pending_genres.json / pending_corrections.json）…

（_sync_data_repo / _push_data_repo）

  • プッシュがぶつかったとき … 自動バージョン更新のActionと競合して失敗した場合、

pull --rebase してから1回だけやり直す

2026-08-14 丸の大きさを知名度で決めるようにした（34/54/85/135/215）。

それまでは手で付けた1〜10の数字の2乗で決めており、知名度とまったく一致して

いなかった（知名度5なのに半径47px、知名度3なのに177pxが混在）。

1段ごとに丸の広さが2.5倍になる案を、2.0倍・1.7倍の案と実際に描いて見比べて選んだ。

2.0倍・1.7倍は全体が平べったくなり、知名度を大きさで表す意味が薄れた。

2026-08-13 知名度は公開データ3つ（ウィキペディアの言語版の数・主要12言語版の

年間閲覧数・代表曲のYouTube再生回数）を数えた合計で決める。AIの感覚では決めない。

以前「影響の強さ」をAIの感覚で出していたときに信憑性を失ったため。

1つでは必ず偏るので3つ使う。重み付けも補正もしない。

2026-08-13 独立した記事が無いジャンルは、閲覧数も1点にする。

親ジャンルのページの閲覧数は、そのジャンルが読まれた数ではないため。

チョロさんの言葉で「他のジャンルから借りるなんていうのは論外」。

例外は「同じジャンルを別の名前で呼んでいるだけ」のもので、

567件中3件だけだった（2-Step / Footwork・Juke / Rage・Rage Beat）。

2026-08-13 パラパラは音楽ジャンルではなくダンスなので、Para Para の記事を

知名度の数字には使わない。ジャンルとしてはユーロビート。

2026-08-13 知名度の根拠は「？」ボタンを押すと吹き出しで出す。パネルの中に

開く形にすると、下にある動画や本文が押し下がってしまうため。

根拠はヘルプ的な情報で、本文を動かしてまで見せるものではない。

2026-08-13 「動きを減らす」設定のときも、？ボタンの光り方は止めない

（ゆっくりにするだけ）。この設定は画面の中で物が動いて気分が悪くなるのを

防ぐためのもので、明るさが変わるだけなら当たらないため。

ただし物が実際に動く見せ方を足すときは、必ずこの設定で止めること。

2026-08-13 別名はジャンル名の下に小さなタグで併記する。

「ヘアメタル」で検索してグラムメタルが出てきたとき、説明文を読まないと

同じものだと分からないのは不親切なため。

2026-08-14 仕様書は「プログラムから読み取れる部分は自動で書き出し、

決めた理由だけ人が書く」方式にする。「その都度きちんと書く」方式は一度

失敗しており、仕様書もヘルプも2026-07-13から1か月止まっていた。

2026-08-18 説明パネルのメイン動画は、そのジャンルの代表曲の中から選ぶ。

「その曲をいっぱい聴きたい」という目的でミックスを探していたが、本当の意味での

ミックスが作られているのはロック・ヒップホップ・フォーク・ディスコのような

よく知られたジャンルだけで、それ以外は名前だけ借りた別物しか無かった

（雅楽に「Japan HipHop mix」、セリアリズムに十二音技法の解説動画）。

再生できないものを外し、代表曲に書かれた演奏者名と合うものを先にしたうえで、

再生回数の多い2本を採る。良いミックスは残す案もあったが、それだと判定が必要になり、

その判定こそが壊れていた原因なので例外は作らない。

2026-08-18 動画を選ぶときは、再生回数だけを根拠にしない。

アブストラクト・ヒップホップのメイン動画は再生1531万回だったが、中身は無関係な

トラップの単曲だった。曲名・演奏者名との一致を先に見て、再生回数はその中での

順位付けにだけ使う。

2026-08-18 地図を開いたときは、配置を保存してあっても必ず全体表示にする。

保存があると全体表示をしない作りだったため、ジャンルが増えて地図が広がると

拡大率100%のまま数個の玉しか映らず、地図が出てこなくなったように見えた。

拡大率を変えるだけで玉の位置は動かさないので、保存した配置は保たれる。

2026-08-24 ファクトチェックの担当を ChatGPT から Genspark の cross_check に

変えた。ChatGPT は文体やリンクIDの直しばかりで、事実の誤りをほとんど拾えて

いなかった。Noise で実測したところ、ChatGPT の指摘は「linksのtarget修正／

descの書き直し／常体に修正」の3つだけで、次の3件を素通りさせ、承認・公開まで

通してしまっていた。Metal Machine Music をヴェルヴェット・アンダーグラウンドの

作品としていた（実際はリードがVU脱退後に出したソロ作）／C.C.C.C. の正式名称を

「コズミック・コンシャスネス・クラブ・クラブ」としていた（正しくは Cosmic

Coincidence Control Center で4語すべて別物）／不失者の結成を1970年代初頭と

していた（正しくは1978年）。cross_check は実際にWebを検索して裏を取り、

この3件すべてを出典URL付きで指摘した。

2026-08-24 事実確認の指摘が出たときは、Claude が内部で本文を直す。人が見て

直すのは二度手間になるため。ただし承認画面には「何が誤りで、正しくは何で、

根拠のURLはどこか」を必ず出す。本文が黙って書き換わると、承認の判断ができない。
